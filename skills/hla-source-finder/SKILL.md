# HLA Source Finder

## 目的
ユーザーが「○○に関するデータを地図に重ねたいが、どこで入手できるか分からない」という初期の探索課題を解消するため、信頼できるデータソース候補（デジタル庁オープンデータ、G空間情報センター、国土地理院、自治体カタログサイト、OpenStreetMap等）の切り口・検索キーワード・候補組織を提案し、ユーザーと対話しながら絞り込む。

※**HLAの最重要原則**: HLAではデータを手元にダウンロード（DL）してローカルコピーを作成するのではなく、**LaWA（レイヤーWebApp）から提供元エンドポイントを直接 `fetch()` してデータのコピーを作成しないこと**が基本原則です。したがって、ダウンロード用ZIP/ファイル配布だけでなく、直接アクセス可能なWeb API、GeoJSON/CSV配信、タイルURL等の存在を最優先で探索します。

※**具体的なデータ・URL・仕様が既にある場合**は本スキルをスキップし、要件定義・設計（`hla-layer-architect`）から直接開始できる。

---

## 安全原則と行動規律
1. **自律的な外部ネットワークアクセスの禁止**
   - エージェントが自律的に外部WebサイトやサーバーへHTTPリクエスト（`curl`, `fetch`, 自動スクレイピング等）を送信してはならない。不正アクセスや意図しない負荷を防ぐため、通信を伴う探索は行わない。
2. **データの非複製（No Data Copy）・直接fetch適性の優先**
   - データを手元にDLして複製・再配布する形態ではなく、LaWAから直接fetchできるURLエンドポイント（CORS許可されたAPI、REST、GeoJSON、XYZタイル等）の候補を優先して提示する。
3. **率直な不明点・不確定性の明示**
   - 不確実なAPI仕様、最新のURL変更、データ更新状態については**「分からない」「要確認」と率直に明示**すること。架空のAPIエンドポイントや存在しないURLを確信ありげに創作（ハルシネーション）してはならない。
4. **ユーザー自身が確認できる切り口の提示**
   - 公式オープンデータポータルの代表ドメイン、検索すべき具体的なキーワード、提供組織名などを提示し、ユーザー自身が手元で検索・確認できる道筋を示す。

---

## データソース候補の探索フレームワーク

ユーザーの要求に応じて、以下の4つの主要カテゴリから適切な接続元候補を検討する。

### 1. 国家・基盤地理空間情報
- **国土地理院 (GSI)**: 基盤地図情報（標高、海岸線、行政区画）、地理院タイル（標準地図、写真、淡色地図、起伏図）。
- **国土交通省 (MLIT)**: 国土数値情報（鉄道、道路、河川、用途地域、避難所、文化財）、PLATEAU（3D都市モデル）。
- **デジタル庁**: ベース・レジストリ（アドレス・ベース・レジストリ、公的施設レジストリ）。

### 2. 自治体オープンデータ・カタログ
- **G空間情報センター (geospatial.jp)**: 官民の多様な地理空間データが集約されたハブポータル。
- **データカタログサイト (data.go.jp)**: 政府・行政機関のオープンデータ統合ポータル。
- **BODIK / 自治体独自カタログ**: 都道府県や市区町村が公開するPOIデータ（AED設置場所、公衆トイレ、避難場所、観光情報、ごみ収集エリア等）。

### 3. 国際・コミュニティオープンデータ
- **OpenStreetMap (OSM) / Overpass API**: 世界規模の道路網、施設、POIデータ。
- **Natural Earth**: 世界・国レベルの広域境界線、海岸線、主要都市ベクターデータ。

### 4. リアルタイム・特定ドメインデータ
- **公共交通オープンデータ協議会 (ODPT)**: 列車・バス・航空機の運行情報、ロケーションデータ。
- **気象庁 (JMA)**: 防災気象情報、降水ナウキャスト、台風進路予想。
- **警察庁・交通安全ポータル**: 交通事故発生マップ、危険箇所データ。

## 絞り込み手順
1. **要求のヒアリングと整理**
   - 可視化したいテーマ、対象地域（全国／特定都道府県／市区町村）、データの鮮度（静的データ／定期更新／リアルタイム）を整理する。
2. **HLA（LaWA直接fetch）での扱いやすさの評価**
   - 手元にDLしてコピーを作成するのではなく、LaWAから直接 `fetch()` して描画できる形式（GeoJSON、CSV、ベクター/画像タイル、Web API等）かどうかを考慮して候補を提示する。
   - 直接fetchにあたりCORS対応状況やAPIキーの要否などを確認ポイントとして整理する。
3. **候補の提示と対話による絞り込み**
   - 2〜3件の有力な候補、想定されるデータ形式、調査用キーワードを提示し、ユーザーの意見や実現したい精度に合わせて絞り込む。
4. **次のステップへの引き継ぎ**
   - 接続元の方向性が定まったら、利用規約や出典表記義務を確認する専用スキル `hla-license-checker` へ引き継ぐ。
