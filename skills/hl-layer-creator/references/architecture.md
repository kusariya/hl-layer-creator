# HLA (HLMap) アーキテクチャ解説書

## 1. 分散型Webマッピング（Hyper-Layering Architecture）の哲学

従来のWebGIS（Leaflet、OpenLayers、Google Maps API、ArcGIS APIなど）は、**「単一のアプリケーションサーバーまたは単一のクライアントアプリケーションが、すべての地図レイヤーとデータを統制する」**という中央集権的（Centralized）なモデルを前提としてきました。

これに対し、**HLA**（およびW3C/OGCコミュニティで発展した **Hyper-Layering Architecture: HLA** / **HLMap**）は、**「World Wide Webそのものの分散アーキテクチャ（ハイパーリンクと自律リソース）」**を地図の世界に適用した革新的なオープン仕様です。

```
【従来のWebGISモデル（中央集権・モノリス）】
+-----------------------------------------------------------+
| 単一Webアプリ (Leaflet/OpenLayers)                         |
|   - 全レイヤーのデータフェッチ (GeoJSON, WMS, MVT)         |
|   - 全レイヤーのスタイリング・レンダリングロジック        |
|   - 全レイヤーのイベントハンドラ・ポップアップ・UI        |
|   - 全レイヤーの状態管理（スパゲッティコード化）          |
+-----------------------------------------------------------+
       ↓                     ↓                     ↓
 [生データA]            [生データB]           [画像タイルC]

【HLA / HLAモデル（分散・フェデレーション・LaWA）】
+-----------------------------------------------------------+
| Container.svg (空間調停コンポジタ / ルース結合)           |
|   - 座標系 (CRS/SRS) の合意                               |
|   - 視域 (viewBox / zoomPanMap) イベントの同期のみ担当   |
+-----------------------------------------------------------+
       | (ハイパーリンク / animation要素)
       +-----------------------+-----------------------+
       ↓                       ↓                       ↓
+---------------+       +---------------+       +---------------+
| 静的SVGレイヤ |       | LaWA レイヤーA|       | LaWA レイヤーB|
| (海岸線ベクタ)|       | (OSMタイルPy) |       | (避難所UI付)  |
|               |       | - 独自HTML/JS |       | - 独自HTML/JS |
|               |       | - 独自DOM生成 |       | - 独自UI/API  |
+---------------+       +---------------+       +---------------+
```

### 分散アーキテクチャの主要メリット
1. **データの非複製（No Data Copy）と最新性の維持**:
   **HLAにおいて極めて重要なのは、「データを手元にダウンロード（DL）してコピーを作成しない」ことです。** 従来のGISではデータを自前PCやサーバーへダウンロード・複製して再配信していましたが、HLAでは各LaWAがオリジナル提供元のURLから直接 `fetch()` してオンザフライ描画します。これにより、データコピーを一切作らず、元データの更新にリアルタイムで追従でき、再配布禁止などのライセンス抵触リスクを回避できます。
2. **サーバーレス・Jamstack親和性**:
   高価で重厚なGISサーバー（GeoServer, PostGIS, MapServer）を必須とせず、静的ファイル（SVG, HTML, JS, JSON）をGitHub PagesやS3、CDNに置くだけで高度なWebGISが動作します。
3. **組織横断のマッシュアップ（Federated Mashup）**:
   自治体Aの「避難所LaWA」、気象庁の「降雨レーダーLaWA」、民間企業の「バスロケーションLaWA」を、サーバー側で結合することなく、クライアントの `Container.svg` がURLを参照するだけで安全に重ね合わせられます。
4. **長期的なソフトウェア寿命**:
   特定のプロプライエタリAPIや巨大ライブラリのバージョンアップ破壊に依存せず、W3C標準（HTML, SVG, ECMAScript, CSS）のみに立脚するため、10年後・20年後もブラウザでそのまま動作し続けます。

## 2. Leaflet / OpenLayers とのアーキテクチャ対比

HLAと従来のWebGISフレームワークの本質的な違いを下表に整理します。

| 項目 | Leaflet / OpenLayers | HLA (HLA / LaWA) |
| :--- | :--- | :--- |
| **パラダイム** | 命令的（Imperative API）<br>`L.map('map')`, `map.addLayer(...)` | 宣言的（Declarative Web Document）<br>`Container.svg`, `<animation>` |
| **レイヤーの本質** | **受動的データ（Passive Data Object）**<br>GeoJSONやタイル配列をエンジンが受領して描画 | **自律的Webアプリ（Autonomous WebApp）**<br>レイヤー自身がデータ取得、変換、描画、UIを完結 |
| **実行スコープ** | **単一グローバルスコープ**<br>すべてのレイヤースクリプトが同じJSコンテキストで競合 | **カプセル化（iframe / LaWA）**<br>レイヤーごとに隔離されたDOM・JS実行空間を保持 |
| **UI（コントロール）**| 地図ビューアの四隅にコントロールをプラグインで追加<br>レイヤー固有UIの分離が困難 | レイヤー自身が独自のコントローラーウィンドウ（HTML）を保有可能 |
| **タイリング機構** | フレームワーク組み込みの固定ロジック（XYZタイル等）に拘束 | 汎用的なQuadTree合成タイリング等をレイヤー側で自由に選択・拡張可能 |
| **データ変換の場** | クライアントのメインスレッドまたはサーバーサイド変換 | レイヤー内部でGeoJSON/CSV等をSVG DOMにオンザフライ変換（`svgMapGIStool`等） |
| **セキュリティ** | 外部レイヤーのコードを無制限に同一コンテキストで実行 | **S-LaWA (Sandbox LaWA)** による同一オリジン分離・XSS防御機構を標準具備 |

### 【重要】Leaflet / 外部ライブラリ併用に関するアーキテクチャ境界線
「Leafletを使ってはならない」という原則は、**「親ページ（中央集権的ビューア）でLeafletインスタンスを生成し、全レイヤーを支配・統括させてはならない」**という意味です。
もし既存資産やLeafletプラグインを活用したい場合、**`appLayer` 等を用いてLeafletのインスタンス・データ・操作ロジックを該当するS-LaWA（iframe）内部に完全にカプセル化し、親ビューアや他レイヤーを侵食しない形**であれば、独立した分散レイヤーとして共存させることが可能です。境界線を越境しないことこそがHLAの本質です。

## 3. LaWA (Layers as WebApps) の核心概念

### なぜ「レイヤーをWebアプリにする」のか？

複雑なGISアプリケーションを開発した経験のあるエンジニアは、以下の問題に直面したことがあるはずです：
- レイヤーA（河川水位）には「リアルタイム自動更新タイマー」と「警告グラフ」が必要。
- レイヤーB（ハザードマップ）には「透明度スライダー」と「浸水深の凡例」が必要。
- レイヤーC（避難所）には「収容人数フィルター」と「検索ボックス」が必要。

LeafletやOpenLayersでこれらを実装すると、メインのJavaScriptファイルにすべてのタイマー、スライダー、凡例、フィルターのコードが同居し、**巨大な神オブジェクト（God Object）とスパゲッティコード**が誕生します。レイヤーCを削除しようとすると、メインスクリプトの各所に散らばったコードが壊れます。

**LaWA（Layers as WebApps）** は、この問題を根本から解決します。
各レイヤーは、以下の要素を1つのカプセルに内包した独立したWebアプリケーションです：
1. **レイヤーのSVGドキュメント (`layer.svg`)**: 空間に配置されるベクターグラフィックス。
2. **レイヤーのコントローラーHTML (`controller.html`)**: レイヤー固有のUI（凡例、スライダー、チェックボックス）。
3. **レイヤーのロジックJavaScript (`controller.js`)**: データのフェッチ、フィルタリング、タイマー、SVG DOMの更新。

コンテナ（`Container.svg`）は、ただ「地図が動いた（`zoomPanMap`）」という空間イベントを各LaWAにブロードキャストするだけです。各LaWAはその通知を受け取り、自分の判断でデータを再取得し、自分のSVG DOMだけを書き換えます。

## 4. コンテナとLaWAの責務分離ルール

HLAの開発において破ってはならない責務境界線（Boundaries）は以下の通りです：

```
[親コンテナ (Container.svg / index.html) の責務]
  ○ 地図描画領域（#mapcanvas）の確保
  ○ 全体CRS（測地系・座標変換行列）の定義
  ○ レイヤーマニフェスト（<animation> 要素による一覧化）
  ○ パン・ズーム操作に応じた視域イベント（zoomPanMap）の発火
  × 各レイヤーの内部データ取得や描画処理には一切関与しない
  × レイヤー固有のUIコントロールを親画面に直書きしない

[各レイヤー (LaWA: layer.svg / controller.html / controller.js) の責務]
  ○ 自レイヤー固有のデータ（GeoJSON, CSV, タイル）の非同期取得
  ○ 取得したデータを自レイヤーのSVG DOM要素へ変換・追加・削除
  ○ 自レイヤー固有のUIコントロール（凡例・操作パネル）の表示・制御
  ○ zoomPanMapイベントに応じた自律的な再描画
  ○ 再描画完了後の svgMap.refreshScreen() の呼び出し
  × 他のレイヤーのDOMやグローバルな地図状態を不正に改変しない
```

この分離を遵守することで、HLAアプリケーションは極めて高い保守性と拡張性を維持できます。
